OptiCore DITA Documentation Architecture

Structured authoring, validation, reuse, and conditional publishing for an optical network controller guide.

Introduction​

Optical Transport Network (OTN) configuration documentation carries a specific set of demands: parameter accuracy is safety-relevant, and procedural content is reused across dozens of near-identical interface tasks. The same content set often needs to serve both customer-facing and internal support audiences without maintaining two parallel docsets.

This article walks through a working DITA-based solution to that problem: the OptiCore Network Controller Guide. It covers the baseline topic architecture, the enforcement and reuse mechanisms layered on top of it, and a custom specialization built to give parameter data real semantic structure rather than generic table markup.

Prerequisites​

RequirementDetail
Oxygen XML EditorAuthor/Text mode; DITA framework support enabled
DITA-OT (bundled with Oxygen)Used for all transformation scenarios (XHTML, PDF, WebHelp Responsive)

Baseline architecture​

Before layering in enforcement, reuse, or specialization, the project starts from a standard, fully validated DITA structure: one concept topic, one task topic, and one reference topic, assembled through a single ditamap. This section is intentionally brief. It exists to establish the working baseline that every subsequent section builds on, not to re-explain fundamental DITA topic typing.

Project structure​

opticore/
  customization/
  maps/
  topics/
    otn-overview.dita              (concept)
    configure-otn-interface.dita   (task)
    otn-parameters.dita            (reference)
  opticore-guide.ditamap

Map assembly​

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE map PUBLIC "-//OASIS//DTD DITA Map//EN" "map.dtd">
<map>
  <title>OptiCore Network Controller Guide</title>
  <topicref href="topics/otn-overview.dita"/>
  <topicref href="topics/configure-otn-interface.dita"/>
  <topicref href="topics/otn-parameters.dita"/>
</map>

This baseline validates cleanly and publishes to XHTML, PDF, and WebHelp Responsive without incident — the starting point for every mechanism documented below.

Schematron constraints for enforcing completeness​

DTD/schema validation defines what content is structurally allowed; it does not enforce what content is mandatory in context. A task's <prereq> and <result> elements are both optional under the base DITA task content model, which means nothing stops an author from omitting either. Schematron closes that gap — a business-rule layer validated alongside, but independent from, the DTD.

Rule definition​

task-constraints.sch:

<?xml version="1.0" encoding="UTF-8"?>
<schema xmlns="http://purl.oclc.org/dsdl/schematron" queryBinding="xslt2">
  <pattern>
    <rule context="taskbody">
      <assert test="prereq">Task is missing a &lt;prereq&gt; element.</assert>
      <assert test="result">Task is missing a &lt;result&gt; element.</assert>
    </rule>
  </pattern>
</schema>

Attaching the rule to a topic​

The Schematron file is bound to a topic via an xml-model processing instruction, placed immediately after the XML declaration:

<?xml version="1.0" encoding="UTF-8"?>
<?xml-model href="task-constraints.sch" schematypens="http://purl.oclc.org/dsdl/schematron"?>
<!DOCTYPE task PUBLIC "-//OASIS//DTD DITA Task//EN" "task.dtd">

The relative href resolves against the referencing topic's own location. The .sch file must sit alongside the topic it constrains, not merely somewhere in the project.

Validation in practice​

With the result removed from the task, validation surfaces the Schematron assertion directly in the Results panel, distinct from any DTD-level error:

A Schematron rule's context determines which elements it evaluates. A rule with context="taskbody" runs against every taskbody in every topic that references the schema — including topics with no relevant content. A rule intended to check a specific data value (for example, a parameter's numeric format) must be scoped to that value's actual element context, not bolted onto an unrelated rule block. Otherwise it produces false positives on unrelated topics.

Extending constraints to specialized content​

Once specialized elements exist (see Advanced implementation with DITA specialization), the same layered pattern applies. A second, independently scoped rule enforces completeness on the new vocabulary itself:

<rule context="otnparamvalue[../otnparamname = 'Optical Power']">
  <assert test="matches(., '^-?[0-9]+(\.[0-9]+)?\s?dBm$')">
    Optical Power must be a number followed by "dBm" (found: <value-of select="."/>)
  </assert>
</rule>

Content reuse using conref and conkeyref​

OTN configuration procedures share recurring fragments across topics — a connection prerequisite, a standard completion result. Duplicating that text per topic risks drift the moment one copy is edited without the others. DITA offers two reuse mechanisms, differing in how the reference resolves.

conref — direct path reference​

common-elements.dita (source fragment):

<reference id="common-elements">
  <refbody>
    <section>
      <p id="otn-connection-prereq">Ensure that the optical node is connected to the Network Controller.</p>
    </section>
  </refbody>
</reference>

configure-otn-interface.dita (conref consumer):

<prereq>
  <p conref="common-elements.dita#common-elements/otn-connection-prereq"/>
</prereq>

conkeyref — key-indirected reference​

conref hardcodes the source file's path. If the file is renamed or relocated, every reference to it breaks. conkeyref adds a layer of indirection through a keydef declared once in the map:

opticore-guide.ditamap (keydef):

<keydef keys="common-result" href="topics/common-elements.dita"/>

configure-otn-interface.dita (conkeyref consumer):

<result>
  <p conkeyref="common-result/otn-config-result"/>
</result>

Relocating common-elements.dita subsequently requires updating one keydef, not every referencing topic — the practical justification for defaulting to conkeyref over conref at any non-trivial scale.

Conditional publishing with DITAVAL filtering​

A single configuration task can contain a step relevant only to internal operations staff (for example, enabling verbose diagnostic logging) that must never reach customer-facing output. Maintaining two separate topics for this is a maintenance liability. DITAVAL filtering publishes two outputs from one source instead.

Tagging the audience-specific content​

<steps>
  <step><cmd>Log in to the Network Controller.</cmd></step>
  <step><cmd>Select <b>Network &gt; Interfaces</b>.</cmd></step>
  <step><cmd>Select the OTN interface.</cmd></step>
  <step><cmd>Set the interface rate to 400G.</cmd></step>
  <step audience="admin"><cmd>Enable debug logging for the interface (admin only).</cmd></step>
</steps>

The filter file​

end-user-filter.ditaval:

<val>
  <prop att="audience" val="admin" action="exclude"/>
</val>

The filter's val attribute matches the tag already present on the content (audience="admin"). The filter targets what is on the element, not the audience the build is intended for. action="exclude" removes the matched element from the generated output entirely, at transformation time. It is not hidden via CSS or client-side logic; it is structurally absent from the resulting HTML/PDF.

The DITAVAL file is attached at the transformation-scenario level (Filters tab of the scenario editor), not at the topic or map level. The same source content can therefore be published through any number of differently filtered scenarios without modification.

Advanced implementation with DITA specialization​

Every mechanism above reuses or restricts DITA's existing element set. None of them can express a genuinely new domain concept: generic <entry> table cells cannot be distinguished as “parameter name” versus “parameter value” structurally, only positionally.

Specialization is the DITA mechanism for introducing new, formally typed elements while remaining valid DITA. An unrecognizing processor gracefully falls back to the specialized element's base type rather than failing.

The three-layer build​

FileRole
otnParamDomain.entEntity declarations: declare the new element names and wire them into DITA's existing extension points (for example, %ph;)
otnParamDomain.modElement/attribute declarations: the actual content models and the class attribute lineage
reference-otnparam.dtdShell DTD: splices the domain into a complete, working copy of the OASIS reference.dtd chain

Domain entity declarations​

otnParamDomain.ent:

<!ENTITY % otnparam-d-ph "otnparam | otnparamname | otnparamvalue">
<!ENTITY otnparam-d-att
  "otnparam-d-att(otnparam otnparamname otnparamvalue)"
>

Domain element declarations​

otnParamDomain.mod:

<!ELEMENT otnparam (#PCDATA | otnparamname | otnparamvalue)*>
<!ATTLIST otnparam
  fecmode (Enabled | Disabled) #IMPLIED
  %univ-atts;
  outputclass CDATA #IMPLIED
  class CDATA "- topic/ph otnparam-d/otnparam ">
<!ELEMENT otnparamname (#PCDATA)*>
<!ATTLIST otnparamname
  %univ-atts;
  outputclass CDATA #IMPLIED
  class CDATA "- topic/ph otnparam-d/otnparamname ">
<!ELEMENT otnparamvalue (#PCDATA)*>
<!ATTLIST otnparamvalue
  %univ-atts;
  outputclass CDATA #IMPLIED
  class CDATA "- topic/ph otnparam-d/otnparamvalue ">

The class attribute is the mechanism's core: "- topic/ph otnparam-d/otnparam " declares that any processor unaware of otnparam should treat it as a plain topic/ph phrase — the specialization's graceful-degradation guarantee.

Splicing the domain into the real OASIS shell​

A shell built from scratch, referencing reference.mod directly, fails immediately. reference.mod assumes a long chain of prerequisite entities (title, shortdesc, prolog, conref-atts, and others) already loaded by the authentic OASIS shell. The correct approach copies the real, working reference.dtd and splices the domain in at the same points other built-in domains (highlighting, programming, software) already use:

<!-- alongside the existing domain entity declarations -->
<!ENTITY % otnparam-d-dec
  PUBLIC "-//OPTICORE//ENTITIES OTN Parameter Domain//EN"
  "otnParamDomain.ent"
>
%otnparam-d-dec;

<!-- extending the existing %ph; domain-extension entity -->
<!ENTITY % ph "ph |
  %hi-d-ph; | %pr-d-ph; | %sw-d-ph; |
  %ui-d-ph; | %equation-d-ph; |
  %otnparam-d-ph;
">

<!-- appended to the included-domains attribute value -->
<!ENTITY included-domains
  "&reference-att; ... &otnparam-d-att;"
>

<!-- domain module integration, alongside the other *-d-def entities -->
<!ENTITY % otnparam-d-def
  SYSTEM "otnParamDomain.mod"
>
%otnparam-d-def;

Because the shell's includes use bare relative filenames (reference.ent, topic.mod, and so on), the shell and its two domain files must reside in the same directory as the authentic OASIS DTD files for those lookups to resolve — not the project's own topics/ folder. In a production setup this is resolved properly via XML Catalog registration or a packaged DITA-OT plugin. Co-locating with the OASIS files is a valid path for proving the mechanism, not the shipping pattern for a team.

Applying the specialization to a topic​

otn-parameters.dita (excerpt):

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE reference SYSTEM "reference-otnparam.dtd">
<reference id="otn-parameters">
  <title>OTN Interface Parameters</title>
  <refbody>
    <section id="otn-params">
      <p>
        <otnparam>
          <otnparamname>Interface Rate</otnparamname>:
          <otnparamvalue>400G</otnparamvalue>
        </otnparam>
      </p>
      <!-- existing parameter table retained below -->
    </section>
  </refbody>
</reference>

The specialized element must sit inside a <section>. refbody does not permit a bare <p> as a direct child. This is a base DITA structural rule, unrelated to the specialization itself.

Fallback behavior in published output​

Publishing the specialized topic through the standard DITA-OT XHTML transformation, with no custom XSLT written for the new domain, confirms the graceful-degradation guarantee directly: the unrecognized otnparam / otnparamname / otnparamvalue elements render as plain inline text, exactly as their declared base type (ph) would.

Layering a constraint on top of the specialization​

Specialization and Schematron are complementary, sequential layers. Specialization creates a distinguishable vocabulary; Schematron enforces completeness on that vocabulary once it exists.

<rule context="otnparam">
  <assert test="otnparamname">Every otnparam must include an otnparamname.</assert>
  <assert test="otnparamvalue">Every otnparam must include an otnparamvalue.</assert>
</rule>
